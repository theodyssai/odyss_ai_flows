# Actions

The framework supports structured action execution directly inside ordinary LLM nodes.

Actions are not implemented as:
- autonomous agents
- hidden execution loops
- opaque tool runtimes
- separate orchestration systems

Instead, actions are:
- structured execution requests
- generated by the model
- validated through structured schemas
- executed explicitly by the runtime

This is one of the most important architectural principles of the framework.

---

# The Core Idea

Actions extend ordinary structured outputs into structured execution requests.

The process conceptually becomes:

```text
render prompt
    ↓
render available actions
    ↓
generate structured action request
    ↓
validate request
    ↓
execute actions explicitly
```

The model does not execute tools directly.

Instead:
- the model proposes structured execution intent
- the runtime executes actions deterministically

---

# Why This Exists

Many workflows require:
- calling APIs
- querying systems
- retrieving information
- performing calculations
- interacting with external services
- composing execution steps

The framework therefore supports:
- explicit runtime actions
- inside ordinary orchestration flows
- without introducing opaque agent runtimes

---

# Actions Are Built on Structured Outputs

Actions reuse the same structured output system used by:

```text
<node_name>.model.py
```

and:

```jinja2
{{ model(...) }}
```

This is extremely important architecturally.

Actions dynamically generate structured Pydantic models which are then processed through the ordinary structured output pipeline.

The provider caller itself does not need to understand actions.

---

# Provider Independence

The Azure caller does not know what actions are.

It only receives:

```python
response_format=model_cls
```

This means:
- actions are provider-independent orchestration semantics
- structured execution remains reusable
- plugins stay decoupled from orchestration concepts

This separation is intentional.

---

# Basic Example

Example:

```jinja2
{{ actions(search_docs) }}

Find relevant information about black holes.
```

The renderer:
- registers the action internally
- renders action descriptions into the prompt
- dynamically builds a structured execution schema

The model then generates a structured action request.

---

# Defining Actions

Actions are ordinary Python objects.

Example:

```python
from odyss_ai_flows import *

from pydantic import BaseModel


class SearchInput(BaseModel):

    query: str


async def search_function(
    args: SearchInput,
):
    return f"Searching for: {args.query}"


search_docs = Action(

    name="search_docs",

    model=SearchInput,

    function=search_function,

    description="""
Search internal documentation
for relevant information.
"""
)
```

---

# Action Components

Each action contains:
- name
- argument schema
- execution function
- prompt-visible description
- execution metadata

Example:

```python
Action(
    name=...,
    model=...,
    function=...,
    description=...
)
```

---

# Prompt-Visible Rendering

Actions are explicitly rendered into the prompt.

This is extremely important.

The model directly sees:
- available actions
- descriptions
- argument definitions
- execution constraints

This avoids:
- hidden runtime behavior
- invisible tool systems
- opaque orchestration logic

---

# Example Rendered Semantics

Conceptually, the prompt receives information similar to:

```text
Available actions:

1. search_docs

Description:
Search internal documentation.

Arguments:
- query: str

You may choose multiple actions.
```

This rendering is generated automatically.

---

# Why Verbosity Is Intentional

The action system intentionally generates extremely verbose structured field names.

Example:

```text
search_docs_action_should_be_executed
```

This is not accidental.

The generated schema participates directly in:
- model reasoning
- semantic clarity
- structured correctness
- validation reliability

The framework intentionally prioritizes:
- explicitness
- correctness
- semantic clarity

over short machine-oriented naming.

---

# Action Modes

Actions support three execution modes.

| Mode | Meaning |
|---|---|
| `MANY` | model may select multiple actions |
| `ONE` | model must select exactly one action |
| `ALL` | all actions must be executed |

---

# MANY Mode

Default behavior:

```jinja2
{{ actions(search_docs, lookup_user) }}
```

The model may:
- execute none
- execute one
- execute multiple

depending on reasoning.

---

# ONE Mode

Example:

```jinja2
{{ actions(
    search_docs,
    lookup_user,

    mode="one"
) }}
```

The model must select exactly one action.

This is useful for:
- routing
- strategy selection
- mutually exclusive execution paths

---

# ALL Mode

Example:

```jinja2
{{ actions(
    summarize,
    classify,

    mode="all"
) }}
```

The model must provide arguments for all actions.

Useful for:
- mandatory processing stages
- required orchestration sequences

---

# Multi-Call Actions

Actions may also support multiple calls.

Example:

```python
Action(
    name="search_docs",
    model=SearchInput,
    function=search_function,
    multi=True,
)
```

This allows the model to request:
- multiple independent executions
- separate argument sets
- parallel action usage

inside one orchestration step.

---

# Example: Multi-Call Execution

Conceptually:

```text
search_docs(
    query="black holes"
)

search_docs(
    query="event horizons"
)
```

Both requests may be generated within the same structured response.

---

# Structured Validation

The framework dynamically generates Pydantic validation models for actions.

Validation ensures:
- required arguments exist
- execution flags are consistent
- multi-call semantics remain valid
- execution requests are structurally correct

This creates much stronger guarantees than:
- plain JSON prompting
- regex parsing
- heuristic extraction

---

# Action Execution

After structured parsing:
- actions execute explicitly
- execution remains ordinary Python
- orchestration remains deterministic

Example:

```python
await action.execute(args)
```

The runtime controls execution, not the model.

---

# Concurrent Execution

`MANY` and `ALL` modes execute actions concurrently using async task groups.

This aligns with the framework's:
- async-first
- concurrency-oriented
- orchestration-native

execution philosophy.

---

# Action Results

Action results are collected into:

```python
handler.action_results
```

and returned from the execution component.

Example conceptual result:

```python
{
    "search_docs": [
        ...
    ],

    "lookup_user": {
        ...
    }
}
```

---

# Failure Behavior

Action failures:
- are logged
- do not automatically fail the node
- produce `None` results for failed actions

This behavior is intentional.

Actions are treated as:
- opportunistic execution augmentations
- rather than mandatory orchestration guarantees

---

# Relationship to Structured Models

Actions internally consume the same structured output slot used by:
- `.model.py`
- `model()`

Therefore these systems are mutually exclusive within a single node.

You cannot combine:

```jinja2
{{ actions(...) }}
```

with:

```jinja2
{{ model(...) }}
```

or:

```text
<node_name>.model.py
```

inside the same node.

This restriction exists because they all define:
- structured output ownership
- response schema semantics

---

# Dynamic Structured Models

The framework dynamically synthesizes Pydantic models from action definitions.

This means:
- actions become fully typed structured outputs
- provider structured parsing becomes reusable
- validation becomes automatic
- orchestration semantics stay explicit

without requiring manually written schemas.

---

# Render Modes

Action descriptions may support multiple rendering modes.

Example:

```python
description={
    "default": "...",
    "compact": "...",
    "verbose": "...",
}
```

Template:

```jinja2
{{ actions(
    search_docs,

    render_mode="compact"
) }}
```

This allows:
- different prompting styles
- different orchestration contexts
- specialized semantic rendering

without redefining actions themselves.

---

# Actions and Pipelines

Actions are pipeline-native.

Typical execution flow:

```text
render
    ↓
actions registered
    ↓
dynamic model generated
    ↓
structured provider call
    ↓
validated action requests
    ↓
explicit runtime execution
```

This keeps actions:
- composable
- explicit
- deterministic
- provider-independent

---

# Actions and Nested Flows

Actions may execute:
- ordinary Python logic
- APIs
- nested flows
- external systems

Example:

```python
async def run_subflow(
    args: FlowArgs,
):
    return await run_flow(
        "subflow",
        ...
    )
```

This allows actions to participate naturally inside larger orchestration systems.

# Design Philosophy

The action system intentionally avoids:
- opaque agent runtimes
- hidden reasoning loops
- autonomous execution engines
- implicit orchestration graphs

Instead, actions remain:
- explicit
- inspectable
- schema-constrained
- runtime-controlled
- execution-deterministic

The model proposes structured execution intent.

The runtime executes explicitly.

This preserves:
- orchestration transparency
- operational predictability
- provider independence
- execution composability

while still enabling sophisticated dynamic execution behavior inside ordinary LLM orchestration flows.

Actions therefore behave as:
- structured execution augmentation
- rather than autonomous orchestration replacement.
