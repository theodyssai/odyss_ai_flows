# Run Naming and Execution Identity

Every flow execution has a runtime identity.

This identity is primarily used for:
- logging
- debugging
- tracing
- observability
- nested orchestration inspection
- loop execution tracking

Run naming becomes especially important once flows begin:
- calling subflows
- running inside loops
- orchestrating reusable execution modules
- executing concurrently
- scaling into larger systems

The framework therefore automatically maintains execution lineage across nested flows.

---

# Top-Level Runs

Every top-level flow execution receives:
- a globally unique internal run ID
- a human-readable run name

If no explicit run name is provided, the framework automatically generates a short unique identifier.

Example:

```python
from odyss_ai_flows import run_flow
import asyncio


async def main():

    result = await run_flow(
        "article_flow"
    )

    print(result)


asyncio.run(main())
```

Possible autogenerated run name:

```text
a13f9d42
```

This ensures all executions remain traceable even without manual naming.

---

# Explicit Run Names

Run names can also be assigned manually.

Example:

```python
from odyss_ai_flows import run_flow
import asyncio


async def main():

    result = await run_flow(
        "article_flow",
        run_name="daily_article_generation"
    )

    print(result)


asyncio.run(main())
```

Explicit names are often useful for:
- scheduled jobs
- API requests
- batch processing
- durable workflows
- observability dashboards
- operational debugging

---

# Nested Flow Naming

Nested flows automatically inherit execution lineage from their parent flow.

Example:

```python
from odyss_ai_flows import *


@node
async def orchestrator():

    result = await run_flow(
        "subflows/process_article"
    )

    return result.outputs
```

If the parent run name is:

```text
daily_article_generation
```

then nested flows automatically receive contextual names similar to:

```text
daily_article_generation, nested in: orchestrator, index: 0
```

This behavior happens automatically and requires no manual orchestration code.

---

# Nested Flows Inside Loops

Automatic indexing becomes especially useful when nested flows execute repeatedly inside loops.

Example:

```python
from odyss_ai_flows import *


@node
async def batch_processor():

    topics = [
        "black holes",
        "dark matter",
        "quantum mechanics"
    ]

    results = []

    for topic in topics:

        subflow = await run_flow(
            "subflows/article",
            topic=topic
        )

        results.append(
            subflow.outputs
        )

    return results
```

Generated nested run names may look like:

```text
daily_article_generation, nested in: batch_processor, index: 0

daily_article_generation, nested in: batch_processor, index: 1

daily_article_generation, nested in: batch_processor, index: 2
```

This makes repeated orchestration execution significantly easier to inspect and debug.

---

# Why Automatic Naming Matters

As orchestration systems grow, nested execution quickly becomes difficult to reason about without execution identity.

Automatic run naming helps:
- correlate logs
- inspect nested execution trees
- debug orchestration loops
- trace reusable subflows
- understand execution lineage
- identify failing nested runs
- distinguish repeated iterations

without requiring developers to manually build tracing systems.

---

# Explicit Naming Inside Nested Flows

Nested flows can still override their automatic generated names.

Example:

```python
subflow = await run_flow(
    "subflows/article",
    run_name="priority_article_generation"
)
```

This replaces the automatically generated nested name for that specific nested execution.

---

# Execution Isolation

Although nested flows inherit execution lineage information, they remain fully isolated execution contexts.

Nested flows do not automatically share:
- runtime inputs
- node state
- flow results
- configuration repositories
- file repositories

unless explicitly passed or configured.

This allows:
- clean modular composition
- reusable subflows
- safe concurrent execution
- predictable orchestration behavior

while still preserving execution traceability.

---

# Relationship to Nested Flows

Run naming is tightly connected to nested flow composition.

As flows become more modular and reusable, execution identity becomes increasingly important.

The framework therefore treats:
- nested execution
- execution lineage
- runtime identity

as built-in orchestration concepts rather than optional debugging utilities.

---

# Practical Usage

Small experimental flows may never require explicit run naming.

However, larger systems often benefit greatly from structured execution identity.

Typical examples include:
- API request tracing
- scheduled orchestration jobs
- durable workflows
- batch processing
- fan-out execution
- multi-stage orchestration systems
- observability dashboards
- production debugging

The framework intentionally provides these capabilities automatically without requiring dedicated tracing infrastructure for basic orchestration visibility.
